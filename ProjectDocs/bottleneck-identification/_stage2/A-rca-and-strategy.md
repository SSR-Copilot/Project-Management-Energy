### SPA-01: Row action (Complete / In Progress / date / comment) holds the overlay for 3 rounds

1. **Current implementation.** `useChecklistWrites.patchRow` (`features/pm/checklist/hooks.ts:475-482`) builds `planChecklistRowPatch` (`rules.ts:1025-1029`, one `guarded: true` update) and calls `w.run` with `invalidate: [qk.checklist(id,"rows")]` (`reload.ts:20-23`). `executePlan` runs the guarded update as `updateRecordIfExists`: existence GET, then PATCH (`executePlan.ts:346-362`, `client.ts:469-513`). `usePlanWrite` (`usePlanWrite.ts:216-229`) returns the reload promise from `onSettled` in the default `"await"` mode, so the mutation, and the full-screen overlay (`Screen.tsx:736 busy = writes.progress !== null`, `WriteFeedback`), end only when the rows refetch has landed. `Screen.tsx:843-850` paints the row green during the write (`completingRowId`).
2. **Root cause (validated).** Execution order: the user waits on a reload of data the write just produced and that the code already holds. The guard GET and the PATCH cannot be reordered or merged (D127 §5; SDK has no `If-Match`, D159 §5). MEASURED (harness, logical rounds): shipped = read@1, update@2, read rows@3 = 3 rounds / 3 requests; all switches off 4 / 11 (`_bench/SPA/checklistVisit.bench.json`). The canvas does not reload (section 3).
3. **Proposed implementation.** (a) New pure function in `rules.ts`: `applyRowPatch(rows, rowId, data)` mapping the four payloads (`completeTaskPatch`, `inProgressTogglePatch`, `completionDatePatch`, `commentPatch`: `CHECKLIST_COL.taskState`, `approvalChecklistState`, `completionDate`, `comments`) onto `ChecklistRow` fields (`taskState`, `approvalChecklistState`, `completionDate`, `note`); unknown columns are not applied. (b) `patchRow` passes `invalidate: [rowsKey]` and `staleOnly: [rowsKey]` (existing `PlanJob.staleOnly`, `usePlanWrite.ts:81`): the key is marked stale, no request is sent now, a mount, a focus or a Refresh reads server truth. (c) The cache is patched inside the job's `then` step (`usePlanWrite.ts:62`, runs after the PATCH landed and before the overlay closes; returns `null`, so no second plan): `qc.setQueryData(qk.checklist(id,"rows",row.clusterStateId), (rows) => applyRowPatch(rows, row.id, data))`, in a try/catch that can never fail the job. (d) `checklistReloadKeys` gets a sibling `checklistRowActionReload` so the template-copy path of `prepareCluster` keeps its awaited rows reload (that path creates rows, it must read them). Switch: `CHECKLIST_PERF.localRowPatch` (default ON in Stage 3 only after the DEV capture; OFF = today's code path, kept, CONVENTIONS rule 15).
4. **Expected technical benefit.** Per click: 3 -> 2 rounds, 3 -> 2 requests; one rows page (up to 40 x 16 columns) no longer downloaded per click. DERIVED from the harness S3 order string. Basis: logical rounds, same method as D150.
5. **User-visible benefit.** The overlay on a click ends one round earlier: about 0.18-0.5 s of the estimated 0.7-1.4 s per click (ESTIMATED, D144 unit costs; the guard GET + PATCH, about 0.43-0.68 s, remain). A user completing 10 tasks saves about 2-5 s in total. Not a seconds-per-click fix, and honestly bounded by the guard.
6. **Dependencies.** D127 §5 guard stays. `usePlanWrite.staleOnly` exists (used by Generators). The proposal reuses `then` for a side effect, which is unusual: Stage 3 may prefer a small `PlanJob.afterWrite?: (qc) => void` hook in `usePlanWrite.ts` (shared file, see section 6). Decision: product owner confirms "the row shows the written state until the next refetch, as the canvas" (DECISION, `DIVERGENCE:` timing/freshness marker, `…CanvasParity` twin = the switch OFF, test, 02-OPEN-DECISIONS entry in Stage 3). The 3 Nov 2026 comment in `Screen.tsx:844-845` ("then the refetched row takes over") shows the reload was a deliberate choice, so ask.
7. **Functional risks.** A server-side change to the row that the screen shows and the client did not write (Modified By/On are in `CHECKLIST_SELECT` but not rendered in the rows; no flow or plug-in fires on `vsb_projectchecklists` rows from this screen, `04-flow-inventory.md`; `SynchroniseProjectTaskList` is triggered by admin template edits, not by this write). Two users on one cluster: user A sees B's change at next focus/mount, as in the canvas. A failed PATCH or a gone row: nothing is patched (the patch runs only after the write succeeded).
8. **Performance risks.** None added. The stale mark makes the next focus refetch rows (already the default for this key).
9. **Complexity.** Low-Medium; about 60 lines (`rules.ts` pure fn + tests, `hooks.ts`, `reload.ts`, flags).
10. **Required tests.** Extend `features/pm/checklist/checklistPerf.test.ts` (UT-CHKPERF-100..103: the reload helper returns the stale-only variant for row patches and the awaited one for the copy; ALL_OFF restores today's list), `hooks.writes.test.tsx` (UT-CHKHOOK-… the four patches: cache shows the written state when `run` resolves, rows key `isInvalidated` and no rows request was sent; a refused or failed PATCH leaves the cache untouched; a gone row leaves it untouched), new `rowPatch.test.ts` (UT-CHKROW-001..006: `applyRowPatch` for each payload, unknown row id, other rows untouched, immutability). Keep UT-CHKPERF-003 (read then PATCH) unchanged.

## 7. Acceptance method for Check List changes (how to pin before/after)

The existing harness is `checklistVisit.bench.test.tsx` (D150, opt-in `CHKBENCH=1`, one worker): it runs the real screen, hooks, TanStack Query, `usePlanWrite`, plan builders and `executePlan`, stubs only the SDK edge at 120 ms per hop, and reports the critical path in logical rounds (a request's depth = 1 + the deepest request completed when it started), plus the request count and the ordered `label@depth` string. It runs every scenario for the `OFF` (all switches off) and `ON` (shipped) variants and fails if three repeats disagree. Acceptance criteria in Stage 3 should therefore quote: scenario id (S1..S8), variant, `rounds`, `requests`, `usableRounds` / `uiRounds` (overlay gone) and the `order` string, e.g. S3 `ON` must change from `rounds=3 requests=3 overlay-gone@3` to `2 / 2 / 2`. Each new switch needs its own always-on, timing-free guard (request-count and order tests in the `hooks.perf.test.tsx` / `checklistPerf.baseline.test.ts` style) so the gain does not depend on the opt-in run. The harness limits: logical rounds, no server or flow time, no Entra latency; the session-probe artefact of section 3 (fixed by T-A08); the bench mocks `@/data/flows` and `data/checklist` loaders, so it cannot show flow time until S7 adds a stub.
