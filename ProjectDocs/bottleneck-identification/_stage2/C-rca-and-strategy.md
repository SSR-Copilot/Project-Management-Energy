## 3. Re-verified facts that change the plan

1. **The prefetch is only worth what the screen's own options allow.** Contracts (`REREAD_ON_VISIT`, `contracts/hooks.ts:34`), the OPEX book (`everyVisit`), OPEX device types (`useCostBook.ts:444`), Finance's four project reads (`finance/hooks.ts:74`) and the admin tree (`FRESH_ON_ENTRY`) re-read on EVERY mount. They are canvas `OnVisible` parity (D109, D120, D123). A prefetch of those keys saves time-to-data, not requests. The plan therefore prefetches default-stale keys first and treats the others separately (section 4.2, rule P3).
2. **Edit Costs always lands on the Summary tab** and on the heaviest Cost read (SCC-11), which is why the Cost entry task matters more than the category book.
3. **Read deadlines do not exist for query reads**, even with `REQUEST_DEADLINES` on (NET-16).
4. **Read pools are a patchwork** (4, 4, 4, 4, 6, 8) and the 17 sites that use `Promise.all` over `chunk(ids)` are exactly the Cost core (`costBook.ts:540,950,1080,1256`, `contracts.ts:178,206,257`, `comments.ts:67`, `landLease.ts:172,177,304`, `opexCatalog.ts:152,161`, `standardContracts.ts:31`, `addCostSheet.ts:146,215`, `currentUser.ts:284`, `adminGatesApprovals.ts:286`). `bulkSend.ts:197` is a write-path verify read and stays out.

### 4.2 What "prefetched data is only valid within staleTime" implies, precisely

A prefetched entry is an ordinary cache entry with `dataUpdatedAt` = the time the fetch FINISHED. When the screen mounts, TanStack decides with the OBSERVER's options (not the prefetch's):

| State at mount | Behaviour | Consequence for the design |
|---|---|---|
| Fetch still in flight | the observer joins it (no restart) | best case: no extra request, data arrives once. This is the common boot case (reads start at t = 0, the gate opens 1-2 waves later) |
| Finished, `now - dataUpdatedAt < observer.staleTime`, not invalidated, `refetchOnMount` not `"always"` | **hit**: data shown at once, no request | default keys (30 s): boot is always inside the window; hover is inside it if the click follows within 30 s |
| Finished, older than the observer's `staleTime`, or invalidated | data is STILL shown at once (until `gcTime`, 5 min), plus a background refetch | no loader, but one duplicate request; the request-count benefit ended at `staleTime`, the no-loader benefit at `gcTime` |
| `refetchOnMount: "always"` or `staleTime: 0` (Contracts, OPEX book, Finance project reads, admin tree) | never a hit; cached data shown, and a re-read always follows unless the prefetch is still in flight | prefetch of these keys saves time-to-data only; **and** a screen that gates behaviour on "this visit's own read has landed" (Finance `fresh`, `isFetchedAfterMount`) gains nothing from a settled prefetch |
| Prefetch started with `staleTime: 0` (those same factories) | `fetchQuery` refetches even a result 1 ms old, so every hover re-fires | intent prefetch must pass a short explicit `staleTime` (10 s) or rely on the dedupe window of E4 |
| A write on the screen invalidated the key while a prefetch was in flight | the late PRE-write answer clears `isInvalidated` (query reducer `success`), so it can be served as fresh | rule P4: the write paths already `cancelQueries` before `invalidateQueries` on the book and totals keys (`useCostBook.ts:721-741`); any new prefetched family needs the same, and a prefetch never starts after its screen mounted |
| Never mounted | the entry lives `gcTime` (5 min) from creation and is dropped | bounded memory, but heavy prefetches (Summary sums, Add Cost sheet: up to 15,000 rows) must not be started on intent |

Rules that follow: **P1** a prefetch factory carries the observer's `staleTime`, because `fetchQuery` uses it for the freshness check. **P2** boot prefetch needs no freshness decision (the window is the gate wait, seconds). **P3** for `always`/`staleTime: 0` keys, prefetch only at boot (the join is likely) and accept one duplicate request when it settled first; do not "fix" the duplicate by treating a prefetch as the visit's read (that is a canvas `OnVisible` divergence and would change Finance's `fresh` seeding guard: DECISION if ever wanted, not proposed). **P4** invalidation coverage as above. **P5** intent prefetch is useful only for default-stale or reference keys, and only if the click follows within the observer's `staleTime`; the telemetry line measures how often it does.

### 4.3 Freshness policy: facts, options, recommendation

### 4.4 Read-side gate and fan-out design

**Constraints (all verified):** Dataverse 52 concurrent requests per user and web server (D165 doc 21; includes every tab and app the user has open); the SDK has no abort, no timeout, no batch; reads of id lists are `ceil(N/40)` requests (`odata.ts:70,78`); the planned `requestGate` (ceiling 40, write lane 24) is entered only by `sendWithPolicy`, which no query read uses; TanStack re-runs a whole query function on retry and cannot cancel a request it started.

**Design.**

| Piece | Design | Reuses |
|---|---|---|
| R1 One read lane for id-chunk reads | New `data/readChunks.ts`: `readChunked(ids, read)` = `chunk(ids)` run through ONE module-level `createGate(READ_LANE)` (initial width **16 = GLOBAL_REQUEST_CEILING 40 - GLOBAL_WRITE_LANE 24**), results in chunk order, and **no chunk starts after a sibling has failed** (waiting chunks check a flag before sending). Adopted by the 17 uncapped sites only; the 8 existing local pools stay (no benefit from touching them) and are listed for later migration | `createGate`, `chunk`, `mapLimit` semantics (`concurrency.ts`); the pattern of `generators.ts:73-79` (`readChunks`) |
| R2 Behaviour-neutral below the width | up to 16 chunks the waves are identical to today (all start together), so Stage 1's wave tests keep passing. Above it the lane queues: a 1,000-contract category goes from 25 + 25 requests in one round to 16 at a time. That trades a few extra rounds for staying under 52, and only where it matters | `costReadPath.waves.test.ts` |
| R3 Consistency with the global gate | 16 + 24 = 40 = the ceiling the gate plans.
